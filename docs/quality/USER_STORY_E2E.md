# MarkText 用户故事与端到端验收

## 1. 产品目标

MarkText 是一个强调速度、可用性和专注写作体验的跨平台 Markdown 桌面编辑器。用户应能从新建或打开内容开始，在所见即所得与源码视图中可靠编辑，组织和检索本地文档，按偏好调整工作环境，并将结果保存或发布，而不会暴露本地系统能力给不可信文档。

## 2. 核心用户

- 日常写作者：希望打开即写、实时预览、自动或手动保存，不因工具打断思路。
- 技术作者：需要精确 Markdown 源码、代码块、图表、数学和 GitHub Flavored Markdown。
- 本地知识库用户：以文件夹管理多个文档，需要文件树、跨文件搜索和多标签页。
- 发布者：需要导出 HTML/PDF 或打印，且输出保留正文和样式。

## 3. 总体用户故事

作为一名在本地管理 Markdown 内容的写作者，我希望从空白页、文件或文件夹快速进入一个稳定的写作环境，在可视化编辑与源码编辑之间自由切换，完成格式化、撤销恢复和检索替换；我希望应用可靠保存我的内容、维护文件和标签页、记住我的显示偏好，并能安全地预览复杂 Markdown 和导出作品，这样我可以从构思到发布都留在同一个快速、低干扰且可信的工具中。

## 5. 验收标准

### US-01 开始并管理本地文档

- `US-01.AC-01` Given 应用使用全新用户数据启动，When 用户输入内容并选择 Save As，Then 目标 `.md` 文件包含输入内容，标签和标题栏显示文件名，未保存标记消失。
- `US-01.AC-02` Given 一个由命令行路径传入的 Markdown 文件，When 首个窗口完成启动，Then 文件正文必须出现，不能显示空白 Untitled 文档。
- `US-01.AC-03` Given 已打开文件，When 用户保存、启用自动保存或更改 LF/CRLF，Then 磁盘内容最终与编辑器一致。
- `US-01.AC-04` Given 已打开文件，When 用户重命名或移动，Then 旧路径消失、新路径存在，标题和后续保存目标同步更新。
- `US-01.AC-05` Given 单标签页，When 用户新建和关闭标签页，Then 活动标签切换正确且至少保留一个可编辑文档。

### US-02 高效写作与修订

- `US-02.AC-01` Given 光标位于正文，When 用户应用标题和粗体，Then 可视 DOM 与保存后的 Markdown 语法一致。
- `US-02.AC-02` Given 用户刚完成一次编辑，When 执行 Undo/Redo，Then 内容先恢复到编辑前，再恢复编辑结果。
- `US-02.AC-03` Given 一个已打开文档，When 用户进入源码模式、修改 Markdown 并返回，Then 富文本视图和磁盘保存结果均包含修改。

### US-03 查找与组织

- `US-03.AC-01` Given 当前文档有多个匹配，When 用户查找并前后导航，Then 计数和活动匹配按 `1 / n` 循环更新。
- `US-03.AC-02` Given 当前文档有多个匹配，When 用户依次执行单次替换和全部替换，Then 计数递减、新文本出现、旧文本消失且文档被标记为未保存。
- `US-03.AC-03` Given 已打开文件夹，When 用户跨文件搜索唯一标记，Then 显示准确的文件数、匹配数、文件名和上下文。
- `US-03.AC-04` Given 命令面板打开，When 用户输入动作名称，Then 首选命令与查询匹配且执行后面板关闭。

### US-04 个性化

- `US-04.AC-01` Given 编辑器已启动，When 用户切换主题，Then 菜单选中状态、主题 CSS 和持久化偏好一致。
- `US-04.AC-02` Given 编辑器已启动，When 用户切换侧栏、标签栏、专注模式和打字机模式，Then 可见状态、菜单状态和编辑器模式一致，且不遮挡编辑区。
- `US-04.AC-03` Given 用户打开偏好页，When 修改自动保存等设置，Then `preferences.json` 更新，当前应用菜单同步。
- `US-04.AC-04` Given 用户逐项打开偏好分类，Then 每个分类可到达，内容在 1280x720 视口内可滚动且无水平溢出。

### US-05 丰富 Markdown

- `US-05.AC-01` Given 文档包含标题、任务列表、表格、代码、链接和数学，When 文档打开，Then 对应语义元素与 KaTeX 结果可见，而不是丢失为纯文本。
- `US-05.AC-02` Given 文档包含 Sequence、Mermaid 和 Vega-Lite，When 异步渲染完成，Then 每种图表都生成可见 SVG，且关键内容可辨认。
- `US-05.AC-03` Given 文档包含链接，When 用户悬停链接，Then 链接工具可见、完整位于视口内且可操作。
- `US-05.AC-04` Given 同一文档含有一个错误扩展块和后续正文，When 扩展块渲染失败，Then 错误状态可见，后续正文仍可读且整个编辑器不崩溃。

### US-06 发布

- `US-06.AC-01` Given 当前文档有唯一正文，When 用户确认 HTML 导出，Then 生成的非空 HTML 文件包含该正文。
- `US-06.AC-02` Given 当前文档可打印，When 用户确认 PDF 导出，Then 打印服务被调用一次，且输出文件以 `%PDF` 开头。
- `US-06.AC-03` Given 当前文档可打印，When 用户确认 Print，Then 当前文档被提交给打印服务一次。
- `US-06.AC-04` Given 导出设置对话框已打开，When 用户按 Escape 取消，Then 设置对话框关闭、正文仍可继续编辑且不调用原生保存窗口。

### US-07 安全与规模

作为维护大型技术文档的写作者，我希望应用只渲染当前需要阅读和编辑的区域，并在我快速跳转时优先完成可见内容，同时保持阅读位置和底部位置不漂移；未访问区域应继续延迟渲染，使输入、撤销和滚动不会因后台完成整篇文档而停顿。无论文档规模或内容是否可信，应用都不能执行嵌入代码、暴露本地系统能力或失去当前工作状态。

- `US-07.AC-01` Given 用户打开含脚本、事件处理器、iframe 和 embed 的恶意 Markdown，When 文档完成渲染，Then 代码不执行、Node 能力不可见、主窗口不导航、不新建窗口且渲染器不崩溃。
- `US-07.AC-02` Given 一个由测试临时生成、大小不低于 700KB 且包含数千分区的文档，When 用户打开它，Then 首屏目标内容可见、当前视口不留 placeholder，远端分区仍保持延迟状态，已挂载真实根节点数量有界。
- `US-07.AC-03` Given 大文档仍有未水合分区，When 用户直接跳到文档中部，Then 中部目标内容在 5 秒内替换可见 placeholder，水合期间同一可见内容的垂直漂移不超过 8px，其他远端分区不被后台递归展开。
- `US-07.AC-04` Given 大文档底部尚未水合，When 用户直接滚动到底部并等待可见内容完成，Then 底部目标可见、当前视口无 placeholder，且滚动位置与底部的距离不超过 2px。
- `US-07.AC-05` Given 只有顶部、中部和底部附近按需水合，When 用户在底部输入并撤销，Then 输入在 1.5 秒内反馈、撤销移除新增文本、远端分区仍延迟渲染且已挂载真实根节点保持有界。
- `US-07.AC-06` Given 用户正在查看仍有未水合分区的大文档，When 用户按 `Ctrl+T`（macOS 为 `Command+T`）新建标签并输入内容后切回原标签，Then 新标签拥有独立且可编辑的空文档模型、渲染器不报错，原大文档内容与延迟渲染状态保持完整。

Worker 创建、消息往返、错误事件以及 preload bridge 的精确键集合属于实现契约，分别由 `contracts/runtime.spec.js` 和 unit 套件验证，不作为用户可见验收标准。

## 6. 横切质量门槛

- 每个测试使用唯一临时用户数据和工作目录，不读取或修改用户真实配置与文档。
- Linux 本地 E2E 必须同时隔离 X11、Wayland、DBus/desktop portal、PID 和 IPC；隔离能力不足时直接失败。
- 等待以用户可见状态或持久化结果为准，不使用固定 sleep 表示“应用已就绪”。
- 原生文件对话框、打印机和外部 shell 在 E2E 中使用主进程边界 stub；测试验证调用参数和最终用户结果。
- 每个故事至少保留一张稳定状态截图。截图前关闭瞬态动画，断言目标状态、无水平溢出、无未处理页面错误，再由人工检查画面。
- 失败时保留 screenshot、trace 和错误上下文；截图不是功能断言的替代品。

## 7. 非目标与补充测试

- 不在 CI 访问真实云图床、GitHub、更新服务器或浏览器；这些边界使用契约或集成测试。
- 不验证物理打印机纸张结果，只验证打印服务收到当前文档。
- 字体、快捷键和原生窗口管理器的全部平台组合由各平台 CI 冒烟覆盖，不在单一 Linux 环境穷举。
- CommonMark/GFM 全规范继续由 spec/unit 套件负责，E2E 只验证代表性内容到 UI 的贯通。

## 8. 完成定义

故事完成需要同时满足：对应功能断言通过、磁盘或主进程副作用正确、无意外渲染器错误、截图人工检查通过、Linux 隔离自检通过，并在本表中能从故事 ID 追踪到测试和证据。任何已知平台限制或未自动化边界必须记录为剩余风险，不能用截图掩盖。

每条 `US-xx.AC-xx` 必须恰好出现在一个 E2E 测试标题中；`test/unit/specs/user-story-e2e-coverage.spec.js` 对文档与故事规格的 ID 集合和唯一性执行静态校验。
