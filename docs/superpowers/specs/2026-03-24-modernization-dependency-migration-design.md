# MarkText 现代化依赖迁移设计

**日期：** 2026-03-24

**目标：** 为 MarkText 制定一条分阶段、可回归、每阶段开发分支始终可运行的现代化依赖迁移路线，最终将项目迁移到现代 Electron 与 Vue 3 生态，并建立长期可维护的升级基线。

## 背景

当前仓库仍建立在一套明显偏旧的应用底座上：

- Electron 18
- Vue 2.6
- Vue Router 3
- Vuex 3
- Element UI 2
- `electron-vue` 自定义脚手架
- 基于 webpack 的定制构建
- 多个与 Node ABI 耦合的原生模块

从仓库结构与入口实现可以看出，这个项目不是“将 package.json 全量升级到最新版后局部修复”的类型，而是需要先重构运行时边界，再迁移构建链与前端主栈，最后将运行时和原生依赖推到当前稳定线附近。

## 明确约束

本设计建立在以下用户确认的约束之上：

- 采用现代化路线，而非保守兼容升级路线。
- 升级按多个阶段拆分，而不是一次性大迁移。
- 每个阶段都必须保持开发分支可运行，且核心功能可回归。
- 阶段中间产物不要求对外发布，不要求终端用户可直接升级使用。
- 接受前端底座迁移：
  - `Vue 2 + Vuex 3 + Vue Router 3 + Element UI 2`
  - 迁移到 `Vue 3 + 现代状态管理 + Vue Router 4 + Element Plus`
- 接受将现有 `electron-vue + webpack` 构建链迁移到现代方案，例如 `Vite + Electron` 组合。

## 非目标

本次设计不包含以下内容：

- 不在本阶段重构 Muya 的内部模型或编辑核心算法。
- 不主动加入与依赖迁移无关的新功能。
- 不在未完成边界收口前提前追求最新 Electron 版本。
- 不在未完成构建链现代化前全面清理所有历史工具链遗留。

## 设计原则

### 1. 先解耦，再迁移，再拉新

任何会同时改变进程边界、构建方式和运行时模型的操作，都必须拆开。避免同一阶段同时进行以下多类高风险变更：

- 框架迁移
- Electron 大版本升级
- 原生模块升级
- 构建链整体替换

### 2. 每阶段都必须有稳定验收线

“可用”不能只等于“能启动”，每个阶段都要满足统一出口标准。

### 3. 迁移优先保证主路径

优先保障核心编辑体验，包括：

- 启动主窗口
- 新建文档
- 打开本地 Markdown
- 编辑
- 保存
- 切换编辑模式
- 打开设置页
- 进入侧栏与标签页交互

### 4. 兼容层是临时手段，不是新常态

允许迁移期间引入 adapter、shim、facade，但必须明确其生命周期和后续删除阶段，避免形成长期双栈并存。

## 当前架构判断

结合仓库内容，可以归纳出几个决定迁移顺序的关键事实：

### Electron 能力与 renderer 耦合较深

renderer 中存在多处直接依赖 Electron 能力或 `@electron/remote` 的代码，例如：

- 窗口控制
- 右键菜单
- 剪贴板
- 偏好设置中的系统能力

这意味着在迁移 Vue 3 或 Electron 大版本前，必须先建立更清晰的 `preload + IPC + facade` 边界。

### 运行时存在多个原生模块

例如：

- `keytar`
- `native-keymap`
- `fontmanager-redux`

这些依赖与 Electron/Node ABI 强耦合，不适合在框架迁移和构建迁移未稳定前同步升级。

### 构建链仍有明显历史包袱

当前工程基于 `electron-vue` 私有脚本与 webpack 定制逻辑。它本身会放大后续升级成本，因此需要在前端主栈迁移前先完成构建层现代化，或者至少先把开发、测试、打包入口迁到现代基础设施上。

### 测试基线偏弱且偏旧

单元测试仍依赖 Karma，e2e 已有 Playwright，但尚未成为迁移主干期间的稳定回归框架。为了让每阶段都可验证，需要先补齐最小 smoke 测试集，并将前端单测逐步迁到现代方案。

## 方案比较

### 方案 A：先升级 Electron，再逐步修复

优点：

- 可以尽快接近新运行时版本。

缺点：

- 在 `@electron/remote`、旧 renderer 假设和原生模块仍存在的前提下，升级风险过高。
- 很难将运行时问题与前端框架问题分离。

结论：

- 不推荐作为主路线。

### 方案 B：先升级 Vue 3 与前端生态

优点：

- 可以较早摆脱 Vue 2 EOL 状态。

缺点：

- 当前 renderer 与 Electron/Node 能力耦合明显，先改 Vue 会把框架迁移与边界重构混在一起。
- 很容易出现大量返工。

结论：

- 不推荐作为首阶段路线。

### 方案 C：边界优先、分层迁移

优点：

- 可将高风险变更拆解到不同阶段。
- 每个阶段都能建立清晰验收口径。
- 最符合“每阶段开发分支可运行”的要求。

缺点：

- 前两阶段用户可见收益不大。
- 需要较强的纪律，避免兼容层长期滞留。

结论：

- 推荐采用该方案。

## 推荐方案

采用“边界优先、分层迁移”的五阶段路线：

1. 进程边界重构
2. 构建链和测试现代化
3. Vue 3 前端迁移
4. Electron/Node/原生依赖拉新
5. 收尾与技术债清理

## 统一阶段验收标准

每个阶段结束前，至少满足以下条件：

- 应用可在开发模式启动。
- 主窗口可打开。
- 可新建文档。
- 可打开本地 Markdown 文件。
- 可编辑并保存文档。
- Muya 编辑视图和源码模式均可进入。
- 标签页、侧栏、设置页可进入。
- 至少保留一条可验证的导出链路，优先以 HTML 导出作为基线。
- 单元测试可通过至少一组稳定子集。
- 最小 smoke e2e 测试通过。
- 该阶段新增兼容层、adapter 或 shim 有明确文档和删除计划。

## 分阶段设计

### 阶段 1：进程边界重构

**目标：** 将 renderer 对 Electron 和 Node 能力的直接访问收口到明确的边界层，为后续迁移提供稳定接口。

**核心动作：**

- 替换 renderer 中对 `@electron/remote` 的直接调用。
- 引入 `preload + contextBridge + IPC` 的统一能力暴露方式。
- 建立 renderer service facade，统一访问：
  - 窗口控制
  - 菜单
  - 剪贴板
  - 文件系统相关桥接能力
  - 字体查询
  - 键盘布局
  - 凭据存储
- 保持现有 Vue 2、webpack、Element UI 与 Electron 主版本基本不变。

**为什么先做：**

- 这是后续所有现代化工作的共同前置条件。
- 如果不先收口边界，Vue 3、Vite、Electron 升级会相互放大风险。

**阶段出口：**

- renderer 不再新增 direct Electron imports。
- `@electron/remote` 使用点清零，或仅保留明确登记的临时例外。
- 主功能 smoke 回归不退化。

### 阶段 2：构建链和测试现代化

**目标：** 将工程运行方式迁移到现代、可维护的构建与测试体系上。

**核心动作：**

- 用现代 Electron 开发方式替换 `.electron-vue/*` 入口。
- 迁移到 `Vite + Electron` 的三段构建模型：
  - main
  - preload
  - renderer
- 为 renderer 引入现代测试体系，逐步将 Karma 单测迁移到 Vitest。
- 保留并加强 Playwright，用于 smoke e2e。
- 将开发、构建、测试脚本切到新入口。

**为什么在阶段 2 做：**

- 没有现代构建与测试基础设施，阶段 3 和阶段 4 的回归成本会过高。
- 先迁底座再迁框架，能减少“构建问题”和“框架问题”交叉影响。

**阶段出口：**

- 日常开发默认使用新构建链。
- `dev`、`build`、`test` 可在新构建链上工作。
- `.electron-vue` 不再是主入口。

### 阶段 3：Vue 3 前端迁移

**目标：** 将 renderer 从 Vue 2 生态迁移到现代前端栈。

**核心动作：**

- `Vue 2 -> Vue 3`
- `Vue Router 3 -> Vue Router 4`
- 状态管理迁移到现代方案，优先考虑 Pinia
- `Element UI -> Element Plus`
- 删除 `vue-electron`
- 删除 `vue-template-compiler`
- 更新应用入口、插件注册、路由和状态注入方式
- 分批迁移核心页面与重度 UI 组件

**为什么在阶段 3 做：**

- 此时边界与构建都已稳定，前端栈迁移可以集中处理 UI 和状态问题。
- 避免与 Electron ABI 或旧脚手架耦合。

**阶段出口：**

- renderer 在 Vue 3 上稳定运行。
- 主页面、设置页、侧栏、标签页、核心编辑交互可用。
- 旧 Vue 2 主依赖不再位于主路径。

### 阶段 4：Electron/Node/原生依赖拉新

**目标：** 将运行时与原生依赖提升到当前稳定线附近，并完成现代 Electron 安全模型落地。

**核心动作：**

- 提升 Electron 到当前支持稳定线附近。
- 同步提升 Node 基线到兼容的 LTS 版本。
- 升级或替换原生模块：
  - `keytar`
  - `native-keymap`
  - `fontmanager-redux`
- 清理旧安全假设，尽量落实：
  - `contextIsolation`
  - `sandbox`
  - 禁止 renderer 直接依赖 `nodeIntegration`

**为什么放在阶段 4：**

- 原生模块与 ABI 耦合最强，必须等应用结构稳定后再处理。
- 此时 renderer 已通过 preload 边界访问系统能力，运行时升级风险可控。

**阶段出口：**

- 目标 Electron 版本下开发、测试、构建可用。
- 原生依赖可在目标平台 rebuild 或打包成功。
- 安全模型达到预期基线。

### 阶段 5：收尾与技术债清理

**目标：** 删除迁移期临时代码，统一仓库的正式运行方式和文档。

**核心动作：**

- 删除迁移阶段遗留的 adapter、shim 和兼容脚本。
- 统一 lint、format、test、build 入口。
- 更新构建文档、架构说明和开发约束。
- 补齐 CI matrix 与版本策略说明。
- 统一清理纯工具和非核心业务依赖的尾部升级。

**为什么需要单独阶段：**

- 如果不单独设阶段，兼容层极易长期滞留。
- 收尾工作直接决定后续升级是否能常规化。

**阶段出口：**

- 仓库只保留一套正式构建/测试入口。
- 文档与实际开发方式一致。
- 临时兼容层已删除，或有明确保留理由。

## 依赖升级策略

### 阶段 1：少动版本，多做边界整理

**优先处理：**

- `@electron/remote` 的调用迁移
- 必要的 IPC/schema/bridge 辅助工具

**暂缓：**

- Vue 主栈
- Electron 大版本
- 原生模块
- 构建主工具链

### 阶段 2：先现代化构建与测试

**优先处理：**

- `vite`
- Electron 与 Vite 的集成方案
- `vitest`
- `playwright`

**过渡保留：**

- 视 Muya 或个别构建细节需要，短期保留局部 webpack 逻辑，但必须登记删除计划。

### 阶段 3：前端主栈迁移

**优先处理：**

- `vue`
- `vue-router`
- 状态管理方案
- `element-plus`
- `@vitejs/plugin-vue`

**删除：**

- `vue-electron`
- `vue-template-compiler`
- `element-ui`

### 阶段 4：运行时与原生模块升级

**优先处理：**

- `electron`
- `electron-builder`
- `@electron/rebuild`
- Node 基线
- 原生模块相关依赖

### 阶段 5：尾部拉齐与清理

**优先处理：**

- lint/tooling 主线升级
- 解析、渲染、导出相关普通依赖
- 安全敏感但不影响主架构顺序的库

## 关键风险与控制策略

### 阶段 1 风险：边界抽象失衡

**风险：**

- facade 只是旧实现的薄包装
- preload API 粒度失控
- IPC 化后暴露异步时序问题

**控制：**

- 只允许通过 renderer service facade 暴露系统能力
- 每收口一类能力就补 smoke tests
- 暂时共存的旧调用必须进入 shrinking scope 清单

### 阶段 2 风险：新构建链能跑 demo，但不稳

**风险：**

- 三段构建边界不清
- 静态资源、动态导入、原生模块处理失配
- 测试环境语义变化

**控制：**

- 允许旧新入口短期并存
- 按 `dev -> test -> build/package` 顺序切换
- 为 Muya 等高风险区块设置独立过渡策略

### 阶段 3 风险：前端框架迁移产生大量表层回归

**风险：**

- Element Plus 行为差异
- 响应式细节变化
- 旧式全局挂载、事件总线、过滤器等失配

**控制：**

- 先迁入口和壳层，再按页面分批切换
- 高风险页面建立页面级 smoke 场景
- 使用 compatibility wrapper 控制状态层切换成本

### 阶段 4 风险：原生模块与安全模型

**风险：**

- ABI 不兼容
- 新安全模型暴露旧逻辑对 Node 环境的依赖
- 平台相关打包差异集中爆发

**控制：**

- Electron 升级按受控跳点推进
- 原生模块逐个验证，必要时直接替换
- 保留各关键跳点的可运行分支或 tag

### 阶段 5 风险：兼容层滞留

**风险：**

- 双栈共存
- 文档和实际入口不一致
- 后续维护仍需依赖迁移背景知识

**控制：**

- 单独设立收尾阶段
- 将遗留项显式列入删除清单并验证

## 推荐实施顺序

推荐采用以下严格顺序：

1. 收口 renderer 与系统能力边界
2. 替换旧构建与测试底座
3. 迁移 Vue 3 前端主栈
4. 升级 Electron、Node 与原生模块
5. 删除兼容层并收尾

该顺序的核心价值在于：每一阶段只处理一种主导复杂度，从而降低回归诊断难度。

## 实施前置要求

在进入实施计划前，需要先补齐以下工程基础：

- 最小 smoke 测试集定义
- 阶段验收脚本定义
- 各阶段临时兼容层登记机制
- 版本基线文档（目标 Node、目标 Electron、目标前端栈）

## 结论

MarkText 的依赖现代化升级应视为一次结构化工程迁移，而不是常规依赖更新。最合理的路线是以进程边界重构为起点，逐步完成构建链现代化、Vue 3 迁移、运行时升级和最终收尾。该路线虽然前期收益不显著，但最能满足“分阶段推进且每阶段开发分支始终可运行”的约束，并能显著降低后续维护和升级成本。
